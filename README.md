# pii-mask

Локальный шлюз маскировки персональных данных перед отправкой текста в облачные LLM - и обратная подстановка оригиналов в ответ. Русскоцентричный: ПД-форматы РФ, NER и морфология русского языка.

**PII** (personally identifiable information) - принятое в отрасли обозначение персональных данных: всего, по чему человека можно опознать - имя, телефон, email, паспорт, ИНН. Отсюда и название: `pii-mask` маскирует именно их.

```
"Иван Петров, тел 8 903 123-45-67, оформи заявку"
        │ pii-mask mask
"{{PERSON_1}}, тел +7 000 000-00-01, оформи заявку"   →  в облачную LLM
        │ ответ модели
"Заявка для {{PERSON_1}} создана, звонок на +7 000 000-00-01 назначен"
        │ pii-mask unmask
"Заявка для Иван Петров создана, звонок на 8 903 123-45-67 назначен"
```

Облачная модель никогда не видит настоящих данных. Основной сценарий - обработка транскриптов встреч (саммари, action items) без утечки имен, телефонов и компаний провайдеру модели.

## Как устроено

Три эшелона распознавания, от дешевого к дорогому:

1. **Regex + контрольные суммы** (форматные ПД РФ): телефон, email, ИНН (10/12, контрольные цифры), ОГРН и ОГРНИП (13/15, контрольный разряд), СНИЛС, карта (Луна), паспорт (только рядом со словом "паспорт"/"серия"), telegram-ник, УИД договора (758-П), а также ФИО в тех формах, которые NER не берет: капсом и с инициалами (см. ниже).
2. **NER** ([Natasha](https://github.com/natasha/natasha)/slovnet, CPU, офлайн): имена и организации. Ключ консистентности - нормальная форма: "Иван Петров", "Ивана Петрова" и "Иваном Петровым" дают одну метку. Одиночное имя ("Иван", "Петров") линкуется к единственному подходящему полному ФИО.
3. **LLM-аудитор** (опционально, `--audit`, Ollama): второй проход по уже замаскированному тексту - "какие ПД остались?". Ловит косвенное: "моя жена Оля", адреса без формата, ники. Модель только предлагает кандидатов (литеральные подстроки), замену всегда делает код.

Принципы:

- **LLM не переписывает текст.** Все замены детерминированные, по спанам.
- **Stateless.** Mapping "метка -> оригинал" возвращается вызывающему (файл рядом с задачей или поле ответа API). Сервис ничего не хранит - нет ни архива ПД, ни TTL, ни "метка протухла".
- **Fail-closed.** Это не фильтр сбоку от трафика, а шаг пайплайна: упал - текст никуда не ушел. Запрошенный `--audit` при недоступной Ollama - ошибка, а не тихая маскировка без аудита.
- **Формат-сохраняющие фейки** для телефонов (`+7 000 ...` - несуществующий код) и email (`userN@example.com`): модель обращается с ними естественно. При обратной подстановке телефоны матчатся и по цифрам - переформатирование моделью не страшно.
- **Защита от выдумок.** Метка или фейк, которых не было во входе, при unmask превращается в `[неизвестное значение]`, а не в чужие данные.
- Пропуск дороже лишней маски: golden-тесты проверяют recall ("ни одна строка из списка не дожила до masked"), ложные срабатывания не считаем ошибкой.

Что сознательно не маскируется: города/страны (LOC) - в рабочих текстах это контекст, а не ПД (включается через `--types`); даты и деньги - без них саммари встречи бессмысленно.

## Установка

Python 3.10+:

```bash
git clone <repo-url> && cd pii-mask
python3 -m venv .venv && .venv/bin/pip install -e .
```

Для `--audit` дополнительно нужна [Ollama](https://ollama.com) с моделью (дефолт `qwen3:1.7b`, переопределяется `PII_MASK_AUDITOR_MODEL`; адрес - `PII_MASK_OLLAMA_URL`, дефолт `http://127.0.0.1:11434`).

## Использование

**CLI, пайплайн транскрипта:**

```bash
pii-mask mask встреча.md                  # -> встреча.masked.md + встреча.mapping.json (0600)
# встреча.masked.md уходит в облачную LLM, ответ сохраняем в summary.md
pii-mask unmask summary.md --mapping встреча.mapping.json -o summary.final.md
```

Повторный `mask` следующего куска диалога с тем же `--mapping` продолжает нумерацию: одна сущность - одна метка на весь диалог. Флаги: `--audit` (LLM-аудитор), `--no-ner` (только форматные), `--types PERSON,PHONE,...`.

**Микросервис:**

```bash
pii-mask serve --port 8377    # слушает только 127.0.0.1
```

- `POST /mask` `{"text": "...", "mapping": null, "audit": false}` -> `{"masked_text": "...", "mapping": {...}}`
- `POST /unmask` `{"text": "...", "mapping": {...}}` -> `{"text": "..."}`
- `GET /health/live` -> `{"status": "ok", "auditor": true|false}`

Тела запросов не логируются. systemd-unit - в `deploy/`.

## Гигиена mapping-файлов

`*.mapping.json` содержит оригиналы ПД. Права 600 ставятся автоматически, паттерн внесен в `.gitignore`. Файл живет рядом с задачей и удаляется вместе с ней - это единственное место, где ПД существуют вне исходного текста.

## Как это соотносится с 152-ФЗ

Вопрос возникает первым, поэтому отвечаем прямо: **шлюз - это техническая мера снижения риска, а не "соответствие закону из коробки".** Разница принципиальная, и продавать ее как compliance нельзя.

**Что он действительно делает.** Закон обязывает оператора принимать меры по защите персональных данных и не обрабатывать больше, чем нужно для цели (ст. 5, 18.1, 19 152-ФЗ). Отправка транскрипта встречи в облачную модель "как есть" - это передача прямых идентификаторов третьему лицу без нужды: модели для саммари не нужны ни фамилия, ни телефон. Шлюз убирает из передаваемого текста именно их, то есть сокращает объем ПД, покидающих контур. По классификации приказа Роскомнадзора №996 это метод введения идентификаторов - замена данных на условные обозначения со справочником соответствия.

**Чем это не является.** Справочник соответствия (`mapping.json`) лежит рядом и позволяет восстановить оригиналы за один вызов. Пока он существует, данные остаются персональными для того, кто им владеет: это псевдонимизация, а не обезличивание в смысле п. 9 ст. 3 152-ФЗ. Отсюда следствия, которые надо держать в голове:

- **правовое основание обработки шлюз не заменяет.** Согласие субъекта, договор, законный интерес - все это нужно ровно так же, как и без него;
- **уведомление и трансграничная передача** (ст. 12) остаются вашей заботой. Замаскированный текст все равно уходит наружу, и если модель зарубежная - это трансграничная передача;
- **квазиидентификаторы остаются в тексте** и никаким регулярным выражением не ловятся: должность плюс город плюс точные даты работы опознают человека без всякой фамилии. Для маленького рынка этого достаточно;
- **обезличенным для свободного использования** результат не становится: чтобы данные считались обезличенными, восстановление не должно быть возможно без дополнительной информации, а у вас она есть.

**Практический вывод.** Правильная формулировка в документах и разговорах с заказчиком - "техническая мера минимизации персональных данных, передаваемых внешнему обработчику", а не "обезличивание по 152-ФЗ". Первое проверяемо и защитимо, второе разваливается на первом же вопросе о том, где лежит справочник соответствия.

Это инженерное описание, а не юридическое заключение: правовую оценку конкретного процесса дает юрист, знающий вашу цель обработки, основание и состав данных.

## Критерии качества

Чем проверяется, что шлюз делает то, что обещает. 36 тестов, прогон - `.venv/bin/python -m pytest -q` (нужны dev-зависимости: `pip install -e '.[dev]'`).

| Свойство | Как проверяется | Что считается провалом |
|---|---|---|
| **Полнота** | Golden-транскрипт: 9 персданных разных форм - ФИО в косвенных падежах, одиночная фамилия, имя без фамилии, email, телефон, telegram-ник | Любая из строк дожила до замаскированного текста |
| **Структура цела** | На том же транскрипте 5 контрольных строк (таймкоды, "Спикер N", заголовки) | Маска съела разметку - текст перестал быть транскриптом |
| **Обратимость** | Roundtrip mask -> unmask, в том числе когда модель переформатировала телефон | Оригинал не вернулся или вернулся в чужую позицию |
| **Отсечение ложных** | 18 тестов распознавателей: ИНН 10 и 12 цифр по контрольным цифрам, СНИЛС по своей схеме, карта по Луну, паспорт только рядом со словом "паспорт" | Номер заказа или артикул превратился в маску |
| **Идемпотентность** | Повторный mask по уже замаскированному тексту | Появился второй слой масок - unmask развернет только верхний |
| **Устойчивость к выдуманному** | Метка и фейковый номер, которых не было в mapping | В тексте остался мусор вместо `[неизвестное значение]` |
| **Границы LLM-аудитора** | Кандидаты ищутся литеральным вхождением, офсеты от модели не принимаются; после прогона модель выгружается | Модель переписала текст, а не предложила спаны |

Реальные ПД в тестах не используются и не должны появляться: golden set (`tests/golden/`) - вымышленные транскрипты.

**Чего эти цифры не значат.** Количественного recall на реальных данных нет: golden set синтетический и маленький, F1 не замерялся. Тесты фиксируют поведение на известных формах ПД, а не долю пойманного на живом потоке - для этого нужен размеченный корпус, которого у проекта нет.

## Официальные документы: акты, реестры, выгрузки

Отдельный класс входа со своими правилами игры - и с провалами, которых нет на резюме и переписке.

**Сначала посмотрите, как извлечен текст.** Это решает больше, чем любое правило внутри шлюза. PDF из таблиц можно превратить в текст двумя способами, и они дают разный результат:

```bash
pdftotext -layout акт.pdf акт.txt   # сохраняет колонки - и рвет сущности
pdftotext          акт.pdf акт.txt  # поток в порядке чтения - сущности целые
```

Замер на одном и том же акте (76 страниц): постранично с `-layout` полных ФИО капсом видно 55, потоком - 879. УИД: обрубков 978 против 11. Реквизит "КПП" и его значение с `-layout` оказываются на разных строках, потоком - рядом. Половина правил ниже написана как компенсация первого режима; если извлечение в ваших руках - берите второй и не создавайте себе работу.

**ФИО пишут капсом.** NER обучен на новостях, там имена в обычном регистре; в таблицах и реестрах они идут прописными, и распознавание падает почти в ноль. Замер на реальном акте проверки (76 страниц): из 55 полных ФИО капсом NER нашел 6. Поэтому такие формы ловятся регулярками, с якорем на суффикс отчества - пара заглавных слов сама по себе именем не считается, иначе именем становится любой заголовок. Отдельно ловится одинокое отчество: колоночная верстка переносит ФИО по словам, и хвост остается в тексте сиротой. Работает и с `--no-ner`.

**Реквизиты идентифицируют не хуже имени.** ОГРН пробивается в открытом реестре за секунды и называет организацию, из которой документ; УИД договора связывает записи между выгрузками. Обезличивание, оставившее их в тексте, бессмысленно - поэтому оба типа в наборе по умолчанию.

У УИД есть неочевидная деталь: в PDF-верстке он рвется по дефису, и хвост может вообще уехать в другое место страницы. На том же акте целыми остались 99 вхождений из 1079 - остальные выглядели как обрубок из двух-трех групп. Поэтому шаблон принимает и обрубок: голова из 12-20 шестнадцатеричных знаков идентифицирует запись не хуже целого номера.

Чего движок по-прежнему не делает на таких документах: не трогает номера поручений, реестров и входящих. Они называют не компанию, а сам эпизод проверки, и в общем случае это часть смысла текста. Нужно закрыть и их - это отдельный набор правил под конкретный класс документов, форматы там жесткие и ловятся регулярками почти без промаха.

## Ограничения

- Метки вместо псевдонимов: в восстановленном тексте имя всегда в именительном падеже ("заявка для Иван Петров"). Псевдонимизация со склонением - возможное развитие.
- NER не всеведущ: экзотические имена и транскрипционные искажения может пропустить - для чувствительных текстов включайте `--audit`.
- Агентные сценарии (модель сама читает файлы) шлюз не покрывает - он для пайплайна "текст туда - текст обратно".
